## Part B — Design corrections
The structure (sidebar, header, cards, tables) stays. Correct the following everywhere, through shared components and tokens, not page by page.

1. Colour discipline. One accent colour (the current blue) for primary actions, links and the active navigation item only. Money and counts are in the normal text colour, not green, purple or orange. Status colours appear only on status: a small badge with a soft tinted background and darker text of the same hue, plus a text label (never colour alone). Remove decorative coloured icon circles from the KPI cards, or make them neutral grey.
2. Active navigation item: a soft tinted background with accent-coloured text and a 2 to 3 px accent bar, not a solid blue block.
3. One language at a time. No mixed labels such as "নগদ (Cash)", "বাতিলকৃত (Voided)", "প্রয়োগ করুন (Apply to All)", "রং \ সাইজ (Colour \ Size)", and no raw enum values such as "CASH", "BKASH", "CARD". Every enum (payment method, sale status, shift status, purchase order status, movement type, role name of system roles) is shown through the translation files in both languages. Keep "bKash", "Nagad", "Rocket" spelled as brand names in English mode and "বিকাশ", "নগদ", "রকেট" in Bangla; cash is "ক্যাশ" in Bangla to avoid confusion with the brand "নগদ". "Walk-in Customer" is translated too. Extend the missing-key test so it also fails when a component renders a hard-coded English or Bangla string.
4. Dates and times. Replace every native <input type="date"> with one shared date picker and one shared date-range picker (shadcn Calendar / react-day-picker, allowed as a dependency). Display format is 16/11/2026 and 16/11/2026, 9:14 AM in both languages, in the tenant time zone, through one shared formatter. No mm/dd/yyyy anywhere.
5. Selects. Replace native <select> elements with the shared shadcn Select (or Combobox with search where the list can be long: category, brand, supplier, product). A filter's empty choice reads "সব ক্যাটাগরি" / "All categories"; a form field's empty choice reads "ক্যাটাগরি বেছে নিন" / "Choose a category". They are not the same string.
6. Typography. Page titles 24 px weight 600, section titles 16 px weight 600, body 14 px, table text 14 px, helper text 12 to 13 px. The Bangla headings are currently too heavy and too large. Line height suitable for Bangla (at least 1.5 for body) so conjuncts and matras are not clipped. Numbers in tabular figures, right-aligned in tables.
7. Tables. Row height about 44 px (one line) or 56 px (two lines); 25 rows per page with a page-size choice of 25, 50, 100; sticky header; zebra or hover highlight; the row itself is clickable where a detail page exists, with the action buttons at the end. Empty cells show "—" in a muted colour. The pagination control is the same component on every list ("1–25 / 142", previous, next).
8. Duplicates. The branch is chosen once, in the header; remove the second branch selector from the dashboard and report pages and let them follow the header (reports may offer "all branches" through the header control). The user name appears once (header menu); remove the copy at the bottom of the sidebar.
9. Payment breakdown. The legend dot of each row has the same colour as its segment of the bar, each segment has a text label or pattern so it does not rely on colour alone, and the method names follow item 3.
10. Dashboard content. "Best-selling items" groups by product with the variant shown underneath, and does not list the same product three times in a row without saying which size and colour each line is. KPI cards show the comparison with the previous day (up or down, with the figure) only if the existing report endpoints can give it without a new endpoint; otherwise leave it out.
11. New-product form. No pre-filled prices (1500, 950 are currently in the fields). Placeholders are translated, in sentence case, and are examples, not values. The variant grid follows Milestone A3 item 3: after sizes and colours are entered, the user sees one row per combination with tick box, suggested SKU (editable), selling price, cost price (only for roles that may see cost) and barcode, with "apply to all" and "apply to this colour / this size". The compact size-by-colour matrix stays for quantities (opening stock, purchase orders), not for entering four different fields.
12. Forms in general. Required fields marked the same way everywhere; errors under the field; primary button bottom right on desktop and full-width at the bottom on phones; cancel is a quiet button to its left. Money fields show "৳" as a prefix inside the field.
13. Phones (375 px). The dashboard date control, the report tabs and every table must be usable: tabs scroll horizontally inside their own strip, tables become stacked cards or scroll inside their container, nothing overflows the page.
14. Dark theme. Check every page in dark theme after the changes: borders visible, badges readable, charts readable, contrast WCAG AA.
Done when: new screenshots of every page are in docs/screenshots/design-v2/ (desktop 1440 px and phone 375 px; light and dark; Bangla, plus English for dashboard, product form, stock list and sales list), the unit and e2e tests pass, and CI is green.

## Part C — The selling screen
Build the screen the cashier uses to sell. Put it in the existing Next.js app under the route /pos with its own full-screen layout (no admin sidebar), using the same sign-in, session, API client, money and time helpers, translations and UI components. The API for it already exists (registers, shifts, cash movements, variant lookup, customers, sales, receipt, void); read the controllers and docs/api-spec.md first. If something is missing, add it under the Milestone A1 rules and log it under API added.

Devices: a Windows PC with keyboard, mouse and a USB barcode scanner, and an Android tablet in landscape (1024 × 768 and up) used by touch. Both run the browser. Offline selling is a later phase: do not build it, but handle a lost connection as described in item 9.

1. Entry and access. Users with sale.create see a "বিক্রি শুরু করুন" / "Start selling" entry in the admin and are taken to /pos; a user whose roles give only counter permissions lands on /pos directly after sign-in. A link back to the admin is shown only to users who may use it.
2. Register and shift. On entry: choose a register of the user's branch (remembered on the device). If the user has no open shift on it, show "Open shift" with the opening cash amount. If a shift is already open for that register by the same user, continue it; if by another user, say so clearly and do not allow selling. The header always shows branch, register, cashier and shift start time.
3. Adding items. One search box that keeps keyboard focus whenever no dialog is open. A barcode scan (fast keystrokes ending in Enter) adds the variant at once, or increases its quantity if already in the cart; an unknown barcode gives a clear message and a sound, and does not clear the box silently. Typing a name or SKU shows matching products; choosing a product with variants opens a size-and-colour picker (the shared grid) that shows the available quantity in each cell and marks out-of-stock cells. Large touch targets (at least 44 px).
4. Cart. Lines with name, size/colour, unit price, quantity (plus, minus, direct entry; decimals only where the product allows them), line discount (percent or amount), line total, remove. Bill discount (percent or amount). Attach a customer by phone number search, or create one with name and phone without leaving the screen; "walk-in" is the default. An optional note.
5. Totals. Subtotal, discounts, tax, total, computed with calculateSaleTotals from packages/shared using the tenant's prices_include_tax setting and the tax class of each product, so the screen and the server cannot disagree. No money arithmetic outside the shared functions. The expectedTotalMinor sent to the server is this total.
6. Limits and permissions. Show the cashier their discount limit. If the combined discount goes over it, warn before payment; if the server answers 403 with DISCOUNT_LIMIT_EXCEEDED or LINE_DISCOUNT_LIMIT_EXCEEDED, show the limit and the attempted figure from the response. Changing a unit price is offered only to users with sale.price_override and is sent as overrideUnitPriceMinor. Do not build a manager-approval (PIN) flow in this task; say so in the log.
7. Payment. A payment dialog with the amount due; methods cash, card, bKash, Nagad, Rocket, bank transfer (from the shared enum). Cash: amount tendered with quick buttons (exact, next round figures), change shown large. Non-cash: amount and a reference field. Split payment across methods is allowed; non-cash amounts cannot exceed the amount due; change is given only against cash. The "Complete sale" button is disabled until the payments cover the total.
8. Completing a sale. Generate the sale id (UUID v7) when the cart is started, send it as body id and as the Idempotency-Key header. Disable the button while the request is in flight. If the request fails by network error or timeout, retry with the same id, so a sale can never be created twice; a 200 for a repeat is success. A 409 (different payload) or 422 (total mismatch, stock, inactive item) shows the server's reason and keeps the cart. After success show the receipt and a "New sale" button; Enter starts the next sale.
9. Losing the connection. Keep the cart in local storage per register so a refresh or a power cut does not lose it. When the browser is offline or the API does not answer, show a clear banner and do not allow completing a sale; adding items already loaded may continue. Never show a sale as completed unless the server confirmed it.
10. Receipt. Use the receipt data from the API, with the shop's header and footer text from settings. Print through the browser with print styles for 80 mm and 58 mm thermal paper (a setting on the device), and an A4 fallback. Bangla must print correctly. Reprint is available from the shift's sales list.
11. During the shift. A list of the current shift's sales with search by receipt number, detail, reprint, and void with a mandatory reason for users with sale.void. Cash in and cash out with amount and mandatory reason.
12. Closing the shift. Enter the counted cash (optionally by note denomination: 1000, 500, 200, 100, 50, 20, 10, 5, 2, 1, summed for the user). Show the breakdown the API returns: opening, cash sales, change given, cash in, cash out, expected, counted, difference, and the totals per payment method. Confirm before closing, print the shift summary, then sign out or return to the register choice.
13. Hold and resume. A cart can be put on hold with a short label and resumed later on the same device (stored locally, at most 10). A held cart gets a new sale id only if it was never sent to the server.
14. Keyboard. F2 focus search, F4 payment, F8 hold, F9 customer, Esc closes the top dialog, Enter confirms the primary action of the open dialog. Show the shortcuts in a small help panel. Do not override browser shortcuts.
15. Language and look. Bangla and English like the admin, same tokens and components, both themes. The layout is two panes in landscape (items and search on the left, cart and totals on the right); the total and the pay button are always visible without scrolling at 1024 × 768 and 1366 × 768.

### POS Tests
- Unit: cart totals equal calculateSaleTotals for mixed line and bill discounts, tax-inclusive and tax-exclusive; change calculation; the barcode-scan handler; the retry keeps the same id.
- End-to-end (own database from Part A): open shift → scan a barcode → add a second item through the size-and-colour picker → line discount within the limit → split payment cash + bKash → receipt shown → stock decreased by the sold quantities → cash out → close shift and the expected cash equals opening + cash sales − change − cash out. A second test: a cashier with a 5% limit tries 10% and sees the limit message, and no sale is created. A third: the request is made to fail once by network error and the retry produces exactly one sale.
- Accessibility check on the selling screen and the payment dialog.
Done when: the tests above pass, screenshots are in docs/screenshots/pos/ (1366 × 768 and 1024 × 768, light and dark, Bangla and English: register choice, selling screen with items, variant picker, payment dialog, receipt, close shift), and CI is green.
