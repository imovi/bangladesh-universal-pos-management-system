Why this phase
The features for the first fashion outlet are built: catalog, sales, offline selling, returns, due sales, transfers, promotions, coupons and loyalty. This phase does not add shop features. Its goal is that the owner can run a real outlet on this system from day one:

it is deployed on a server;
it is backed up, and a restore has been proven to work;
receipts print on a thermal printer;
the existing products and customers can be imported;
when something breaks, someone finds out.

No credentials. Never read, print or use any credential, token, SSH key, cloud account or Git Credential Manager entry on this computer. You cannot reach a real server or cloud account, and you must not try. Everything in this phase has to run and be proven on this machine with Docker, and in CI. Milestone F2. Backups that are proven to restore (about 1 hour)
A backup that was never restored is not a backup.

Backup. The backup service runs pg_dump --format=custom every night at 02:30 Asia/Dhaka, and also on demand with npm run backup:now.

Encryption: the file is encrypted with age, using a public key from env. The private key never goes on the server; the docs say where the owner keeps it.
Retention: 14 daily backups and 8 weekly ones.
Off-server copy: rclone copies to a remote named in env (BACKUP_RCLONE_REMOTE). If none is configured, a loud warning goes in the logs and on the admin settings page: "ব্যাকআপ শুধু এই সার্ভারে আছে". Do not configure any real remote.
Restore. scripts/restore.sh <file> decrypts the file and restores it into a new database. It never restores into the live one. It then prints row counts for the core tables, so the operator can switch over by hand. The switch-over steps are written in the docs.

Roles and RLS. The restore drill must prove that pos_app, pos_runtime and pos_admin, their grants and every RLS policy come back. A plain pg_dump of one database does not include roles, so handle this: dump the globals separately, or re-run the role init, and write down which.

Restore drill in CI, as a test:

seed the demo tenant into *_restore_check;
back up;
drop;
restore into a fresh database;
check that row counts match for the tenants, products, variants, sales, sale items, stock movements, loyalty ledger and audit log tables;
check that tenant A's token still cannot read tenant B's data through the API pointed at the restored database;
check that audit_logs and loyalty_ledger are still append-only.
Admin page. On /settings, add a "Backups" card, readable only by Owner, showing:

last backup time and size;
whether an off-server copy is configured;
the last restore-drill date, if one is recorded.
It is read-only and has no download button. Backups stay on the server.

docs/go-live/backup-restore.md: how to check backups, run a restore drill once a month, and recover after a dead server.

Milestone F3. Thermal receipt printing and cash drawer (about 1.5 hours)
Today receipts print through the browser's print dialog. A real counter needs one-tap printing to an 80 mm or 58 mm thermal printer, and the cash drawer must open on cash sales.

Bangla text. Most cheap thermal printers have no Bangla font, so Bangla text must be sent as an image:

Render the receipt to a canvas at the printer's width (576 dots for 80 mm, 384 for 58 mm).
Convert it to 1-bit, with a threshold or dithering, and keep it sharp.
Encode it as ESC/POS raster (GS v 0).
Add a "text mode" for English-only receipts, which is faster.
One shared encoder. Write a pure function in packages/shared (or apps/admin/src/lib/printing). The input is the receipt model plus printer settings, and the output is Uint8Array. It includes:

init;
the raster image;
feed;
partial cut;
drawer kick (ESC p 0 25 250), only when the sale has a cash payment, so not for bKash-only or points-only sales.
Unit tests for the encoder:

exact byte headers;
the raster width and height bytes for 80 mm and 58 mm;
the drawer kick present or absent by payment method;
a golden-file test comparing the bytes for one fixed sample receipt.
Transport. All of these live behind one printer interface, and /pos calls only that interface:

Web Serial and WebUSB, in Chrome and Edge on Windows;
network printers: raw TCP 9100 is not possible from a browser. Do not build a local agent; write this down as a limit.
fallback: today's browser print dialog.
/settings/printer page. Pick the connection type and paper width, then:

"Connect" uses the browser's device picker;
"Test print" prints a sample receipt with Bangla text, a ৳ sign and a barcode;
"Open drawer";
auto-print after a sale, on or off;
number of copies.
Settings are stored per register in local storage, like today's paper size.

Offline. Printing must work when offline. It needs no network.

Hand-test list. The real printer cannot be tested here, so write docs/go-live/printer-setup.md with:

Windows driver notes;
how to find the printer in Chrome;
what to do when Bangla prints as boxes, when it prints blank, and when the drawer does not open;

Milestone F4. Data import for day one (about 1.5 hours)
The shop already has products, stock and customers who owe money. Typing them in by hand would take days.

CSV import in the admin, under /settings/import, for:
Products with variants: one row per variant, with columns product name, category, brand, collection, size, colour, SKU, barcode, sale price, cost price and VAT rate.
Rows with the same product name group into one product.
A size that is not yet in the size order is added to it.
Opening stock: SKU or barcode, branch code, quantity and unit cost. This creates OPENING stock movements, or the closest existing movement type; log which one.
Customers: name, phone, opening due, and opening loyalty points.
The opening due goes into the customer ledger.
The opening points become one ADJUST entry with reason "opening balance".
Two steps: preview, then commit.
Preview: upload, see every row as OK or error, with the reason in Bangla and English (bad price, duplicate barcode, unknown branch, a phone not in Bangladeshi format). Error rows can be downloaded as a CSV.
Commit: runs only if the preview has 0 errors, and only in one transaction per file. Either everything goes in or nothing does.
Safe to repeat. Importing the same file twice does not create duplicates: match products by SKU and customers by phone. A second import of opening stock for the same SKU and branch is refused, with a clear message.
Encoding. Accept UTF-8 with or without BOM, because Excel saves CSV with a BOM, and Bangla text must survive. Prices may be written as 1,200, 1200 or 1200.00; amounts are stored in poisha.
Size limit. Up to 20,000 rows per file. Show progress.
Permission. Owner only, with a new permission data.import, and an audit entry for each commit with the row counts.
Templates. Download links for the three CSV templates, each with 3 example rows in Bangla.
Tests:
the parser, with BOM, Bangla text, the price formats and bad rows;
API: the preview shows the errors and commit is refused while errors remain;
API: a 5,000-row import completes in under 60 s locally;
the re-import does not duplicate;
tenant isolation: an import never touches another tenant;
one Playwright test: upload the template, preview, commit, then the product is visible on /pos and its stock is correct.
